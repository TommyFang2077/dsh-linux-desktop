# alpha.1 到 alpha.2：过渡升级与恢复

本轮冻结归档、实际 UI/进程链路、完整恢复、写入者负例与审查结论见 [隔离验收记录](desktop-migration-verification.md)。该记录区分源码交付与生产发布。

## 发布状态与适用范围

这里记录本轮确认的升级方案与验收要求。源码改动、本地构建和隔离验收不等于生产更新源已经发布；真实发布与用户安装切换分别确认。

适用起点为 `0.2.1-alpha.1 · Linux r7`。alpha.2 引入持久化记录与工作目录变更，继续使用独立的 `dataEpoch`，不通过修改兼容声明来放行旧内核。本次非空记录读取验收覆盖两版本共同的会话格式 v4；它不是格式转换，也不代表所有新写入记录都支持旧版本回读。

## 应用内升级顺序

1. 旧客户端从原有签名桌面更新源获取 `alpha.1 · r8` 过渡包。该包使用固定的 alpha.1 官方源码与内核，只回移新版更新器和迁移支持；内核、桌面、协议和数据格式仍属于 alpha.1。
2. 过渡版本从独立的 alpha.2 更新源检查完整桌面归档。本轮修复后的目标为 `alpha.2 · Linux r2`，与已经发布的 r1 资产分开。跨数据格式升级使用明确的整包升级入口，普通内核和桌面更新继续执行原有兼容检查。
3. 下载并验证归档后，提示用户关闭共享此数据目录的其他 dsh 或 CLI，确认停止当前任务并重启。取消、任务停止失败或移交进程准备失败时保持当前版本。
4. 迁移进程接管归档的生命周期。旧 Host 干净停止、旧 Electron 进程实际退出后，才开始备份；收到退出通知或安排重启均不等于进程已经退出。
5. 完整备份运行时实际使用的 DSH 数据根和 Electron 用户数据根，验证备份成功后才切换 HOME 程序，并启动明确的新版本路径。

迁移不调用 sudo、pkexec 或包管理器，不重置配置、会话、插件或受信签名公钥。只更新 deb/rpm 引导载荷也不会替换已有 HOME 安装。

## 备份约定

- 默认位置：`$HOME/Backups/dsh-workbench/` 下的独立事务目录。
- 目录仅当前用户可访问；备份保留到用户手动删除，不自动清理。
- 数据根来自运行时路径解析，使用实际 `DSH_HOME` 和 Electron `userData`，而非猜测 `~/.dsh` 或某个 `.config` 目录。当前迁移要求这些根为 HOME 内的绝对路径；HOME 外的覆盖路径会明确停止迁移，不忽略该数据根。
- 备份位置与数据根、程序安装根相交时停止升级。
- 空间不足、权限错误、异常文件、校验失败、其他共享写入者或备份期间数据变化均停止切换。
- 备份必须经过完整验证和完成标记；复制开始、临时目录存在或备份进程已启动均不代表成功。
- 数据符号链接保存原有链接内容，外部目标保持不跟随。当前迁移会在复制备份和切换前停止 HOME 内绝对数据链接的布局；明确调整为相对链接或迁移该布局后再重试，避免升级后才发现它仍指向原 HOME。
- 安装指针仅支持指向已备份程序的目标；正常相对链接保持相对，HOME 内绝对安装指针可在恢复时重定位。外部或未备份的安装目标在切换前停止迁移。

桌面启动保护与当前 Host 的任务锁不等于所有第三方 CLI 都遵守同一个锁。用户须先关闭共享数据根的其他写入程序，并在迁移期间保持关闭；检测到已知写入者或数据变化时停止升级。

迁移还检查同 UID 的真实 `/proc` 状态。活动进程的文件描述符不可读时，报告 PID 和错误路径并停止切换；这表示尚未证明没有其他写入者，并不表示该进程已被确认正在写数据。只有明确处于 zombie 状态、已没有文件描述符的进程可排除。

共享可写内存映射同时比较路径与设备号/inode。数据根外的硬链接别名即使已关闭文件描述符，只要仍持有同一文件的 `MAP_SHARED | PROT_WRITE` 映射，仍停止备份和切换；删除别名也不绕过此检查。私有可写映射与共享只读映射本身不会被判定为数据写入者。

本机实际宿主验收中，PID 1950 是 UID 1000 的用户 `systemd`，读取 `/proc/1950/fd/0` 返回 `EACCES`；worker 停止且旧程序指针和数据保持原样。关闭其他 dsh/CLI 本身不会消除这一权限前提。成功端到端验收限定在非 root PID namespace，证明升级及整组恢复链路；当前默认宿主仍受该进程可观测性条件阻断，发布说明须同时列出这一条件和中止行为。

## 失败与恢复

切换前失败保持旧程序和原数据，记录失败原因。若旧程序已经退出，按事务报告处理，不把未完成的备份标为成功。

新版本启动后可能已经迁移数据。因此，启动或健康检查失败时保留备份与事务报告，不静默切回旧数据格式的程序。回到 alpha.1 时必须先停止所有相关进程，恢复对应事务的整组数据与程序状态，再启动旧版本。仅切换 `current` 或内核指针并不是数据恢复。

恢复操作应先在独立目录核验备份清单与数据格式，再明确执行。多数据根恢复需要逐项记录进度；中断后先核对事务状态，避免让旧内核读取已迁移的新数据。

事务目录保留独立的 `worker.mjs` 和 `transaction.json`。使用报告记录的旧 bundled Node 绝对路径执行生产恢复入口；普通 Node 可读取此实体模块，无需从源码导入内部助手。先核验，再恢复到新的空私有 HOME：

验证同时约束清单路径：数据根须匹配事务记录，旧程序根须匹配已记录的 `current/previous`，安装入口须匹配固定的备份路径。含 `..`、非绝对路径、NUL 或被改向其他目录的映射在创建恢复 HOME 前停止；写入时再次检查目标位于恢复 HOME 内，且没有符号链接祖先。

公开验证与恢复共用安装链接检查：`current` 必须指向原安装状态记录的完整程序根；`previous` 存在时同样精确匹配原版本，为空时须保持缺失。指向其他已备份版本或某个程序子目录也会停止。其他安装链接须位于已备份程序内，验证入口据此提前报告错误，而非等到恢复时才发现。

```bash
NODE=/absolute/path/to/old/bundled/node
TX="$HOME/Backups/dsh-workbench/TRANSACTION_ID/transaction.json"
WORKER="$HOME/Backups/dsh-workbench/TRANSACTION_ID/worker.mjs"
RECOVERY_HOME=/absolute/path/to/new-empty-recovery-home
"$NODE" "$WORKER" verify "$TX"
"$NODE" "$WORKER" restore "$TX" "$RECOVERY_HOME"
```

`verify` 成功输出 `verified: true`；`restore` 成功输出 `restored: true` 与恢复后的实际数据路径。对通过上述布局检查的事务，恢复覆盖完整两组数据、旧程序树、安装状态、`current/previous`、launcher 与桌面入口，并把安装相关绝对路径重定位到恢复 HOME。CLI 只写新的空 HOME，不自动覆盖源数据、不自动切回源安装的旧 `current`。历史备份若包含 HOME 内绝对数据链接，`verify` 仍核验原链接内容，但跨 HOME 的 `restore` 会在创建目标前停止；此类备份的原地整组恢复须明确停止相关进程后手工处理。

验证可运行的旧程序时，使用恢复输出 `roots` 数组中名称为 `dshHome/userData` 的实际 `path`，并为 HOME、DSH_HOME 和全部 XDG 目录设置恢复 HOME 下的路径；清除 `ELECTRON_RUN_AS_NODE` 与迁移事务 token，再运行 `$RECOVERY_HOME/.local/bin/dsh-workbench`。启动前比较完整恢复清单，启动后验证旧 Host 健康与数据，不把一个正确的 symlink 当作完整恢复。

## 双更新源

原有 `desktop-latest.json` 和 `kernel-latest.json` 保留给真实 alpha.1 r8 过渡链，保持旧客户端认识的签名格式和受信公钥。r8 的普通检查继续使用这两个旧源，只有独立的 `desktopUpgrade` 使用 alpha.2 源。alpha.2 的普通通道使用 `desktop-dsh-0.2.1-alpha.2-latest.json` 和 `kernel-dsh-0.2.1-alpha.2-latest.json`；只有完成签名与资产发布后才切换线上文件。

已发布的 alpha.2 r1 与 alpha.1 r7 都请求同一个静态地址，且没有携带版本身份；一份静态根清单无法同时声明两个不同的数据格式。已发布 alpha.2 r1 因此需要显式切换更新配置。`DSH_WORKBENCH_UPDATE_CONFIG` 支持绝对路径的配置覆盖，完全退出后再启动生效；保留原有公钥，切换更新源不等于更换信任来源。

发布对应 epoch 文件之后，可从本仓库已核对公钥的 `updates.json` 提供配置覆盖；这不是绕过兼容检查，也不会使尚未发布的 URL 自动生效：

```bash
DSH_WORKBENCH_UPDATE_CONFIG=/absolute/path/to/dsh-workbench/updates.json \
  "$HOME/.local/bin/dsh-workbench"
```

## 验收要求

- 冻结真实 r7 更新器，验证其 `check/install` 能消费旧格式签名的 r8 过渡包。
- r8 与 alpha.2 的源码、版本、内核、数据格式、Linux 构建号和归档身份分别匹配。
- 从生产整包升级入口执行真实外部迁移进程，不以复制助手或模拟重启代替完整调用链。
- 观察顺序为：准备完成、干净停止、原 Electron 实际退出、备份验证、程序切换、新程序启动。
- 使用完全隔离的 HOME、DSH_HOME 和 XDG 目录验证升级、启动、失败保持与旧格式备份恢复；真实安装和数据保持不变。
- 错误签名、混包、错误数据格式、取消、退出失败、备份失败和共享写入者均有明确失败证据。

具体命令、产物摘要和实际通过结果在验收完成后记录；本页中的设计要求不替代运行证据。

真实 worker 成功测试需要 Linux `unshare` 和允许非 root user/PID namespace。测试文件自行创建 namespace，保留真实 `/proc` 检查和 Chromium sandbox；能力缺失时正例明确失败，不跳过。宿主不可读进程门禁另做独立失败保持验证。完整桌面验收须明确记录 namespace 环境，不能由隔离成功推断当前宿主门禁也会通过。
